# Sylp provenance: see how your code came to be

Local-first, open-source code provenance for AI coding agents. Click a code change and see the prompt, the assistant response and the tool action recorded around it. One small recorder works with Claude Code, Codex CLI and Cursor CLI; an evolution timeline shows how the repository grew - prompts, tool windows, file changes, commits and branches in one view - and a localhost dashboard lets you watch it live.

**Why it exists:** AI agents write more of our code every day, and the reasoning behind each change disappears with the session. Provenance keeps the why next to the what, on your own machine, with nothing uploaded.

Inspired by delta.dev's "See how the code came to be". Delta is a hosted product by Zed Industries; this is not Delta, is not affiliated with it, implements only that one idea, and claims no Delta compatibility or parity. Other open-source projects explore the same space for a single host (for example promptrail and git-for-prompts); this spike's angle is three hosts from one recorder, evidence labels that keep unknowns unknown, and zero dependencies beyond Python's stdlib and SQLite.

## Status

Private experiment. Fixture-tested (30 checks, simulated hook payloads driving real file edits), **not yet verified in a live CLI session**. Hook event names and payload fields differ between hosts and may change between CLI versions. Use it only in a disposable repository.

## See it

The rendered demo page is committed at [examples/history.html](examples/history.html); download it and open it locally.

It is generated by `python3 demo.py /tmp/sylp-demo` with synthetic hook payloads - a fixture, not a live CLI session. One session, five prompts, Edit and Bash tool windows, a failed command, one linked change per prompt, one manual edit the hooks never saw (labeled unattributed), and three commits by two authors: inside a tool window (possibly agent-made, not proven), during a recorded session, and outside recorded sessions.

## Watch it live: sylp serve

`python3 recorder.py serve` starts a read-only, localhost-only dashboard at http://127.0.0.1:8777 and opens it in your browser. It lists every recorded repository under `~/.sylp-provenance` so you can pick which one to view, shows recorded usage per repo (sessions, prompts, tool calls by name, changes, commits at render time), and auto-refreshes every 10 seconds while your agent works. Token counts and cost are not exposed by host hooks, so they cannot be shown. It writes nothing and nothing leaves the machine. Once the plugin is installed you can also ask your agent to open the dashboard: `/sylp-provenance:serve` in Claude Code and Cursor, or the `serve-dashboard` skill in Codex. `render` remains for a shareable static export.

## Ask why: the MCP server and `sylp why`

The recorder doubles as a stdio MCP server, so your agent can answer "why is this here" from recorded evidence:

```sh
python3 recorder.py why path/to/file.py --line 42     # or: recorder.py mcp  (stdio server)
```

`why` blames the line (or the file's latest commit), then matches the commit's blob content exactly against recorded snapshots. It reports the recorded prompt, tool action and evidence label on an exact match; the nearest earlier recorded change with a clear "not an exact match" caveat when content moved on; and "no recorded session" when nothing matches. It never guesses.

The plugin wires the server per host: Claude declares it inline in `.claude-plugin/plugin.json`, Cursor ships `mcp.json` (both use documented plugin-root variable expansion), and Codex ships `.mcp.json`, whose plugin-relative path expansion is not documented for Codex - if Codex does not pick it up, `install.py` prints an absolute-path `codex mcp add` fallback. MCP wiring is docs-based and not verified against live host sessions.

## PR evidence

`python3 recorder.py pr-summary main..HEAD` prints markdown listing each changed file with its recorded prompts and evidence labels, and flags files with no recorded prompt (which are not necessarily human-written; capture may not have seen them). The output contains private prompt text and says so; `--no-prompts` redacts it. The plugins ship a `pr-evidence` command (Claude, Cursor) and skill (Codex) that draft this summary and never open a PR by themselves: creating or updating a PR requires the user's explicit per-PR approval after reviewing the summary.

## Quick start

Needs Python 3.10+ and git. One clone today (publishing to a marketplace would remove it; see Status), then each host installs natively. No per-repo setup: once the plugin is enabled, its hooks record every repo you open in that host, each into its own database under `~/.sylp-provenance/repos/`, created on the first hook event.

```sh
git clone -b experiment/code-provenance-adapters https://github.com/seanbenhur/sylp.git ~/sylp-prov
```

**Claude Code** (native install, two commands):

```sh
claude plugin marketplace add ~/sylp-prov/experiments/provenance
claude plugin install sylp-provenance@sylp-provenance
```

**Cursor CLI** (`agent`): Cursor has no CLI install command for local plugins, so the plugin folder is copied once into its documented local-plugin location:

```sh
cp -R ~/sylp-prov/experiments/provenance/plugins/cursor ~/.cursor/plugins/local/sylp-provenance
```

(install.py does the same copy). A true one-command install needs the Cursor Marketplace, which is publishing.

**Codex CLI**: Codex's local flow needs its personal-marketplace files written once; the installer does exactly that and nothing else:

```sh
python3 ~/sylp-prov/experiments/provenance/install.py --host codex --marketplace
```

Then open `codex`, run `/plugins` to enable sylp-provenance, and `/hooks` to trust its hooks (Codex skips untrusted hooks). That flow is written from the official docs and is not verified against a live Codex install.

## Use it, from inside the agent

Open any repo in your agent and work as usual; the hooks record automatically. Then:

- Ask **"why is this line here?"** - the agent answers through the plugin's MCP server from recorded evidence, with honest "no recorded session" when there is nothing.
- **Dashboard**: `/sylp-provenance:serve` (Claude, Cursor) or the `serve-dashboard` skill (Codex) starts the read-only localhost dashboard.
- **Demo without spending quota**: `/sylp-provenance:demo` builds a synthetic throwaway session under /tmp and renders it.
- **PR evidence**: `/sylp-provenance:pr-evidence` drafts a per-file provenance summary; it never opens a PR by itself.

Heads-up: while installed, the plugin records prompts and code from every repo you open in that host. `recorder.py pause` pauses a repo's database; uninstall removes capture entirely. Captured text stays local and unencrypted - prefer throwaway repos until you trust it.

## Scripted install alternative

`install.py --host <cursor|codex|claude> --repo <dir>` still sets up any host in one step, including a throwaway repo and project-scoped Codex hooks (`.codex/hooks.json`) when you want capture in one repo only. Rendering a static export from inside a recorded repo: `python3 ~/sylp-prov/experiments/provenance/recorder.py render ~/history.html`.

**Let your agent test it.** Paste [TESTING-AGENT-PROMPT.md](TESTING-AGENT-PROMPT.md) into your agent: it installs the plugin into a throwaway repo, runs one small recorded prompt, renders the history page and reports pass or fail with exact errors. It states the quota cost first and waits for your go-ahead. The same steps ship as a skill at [skills/sylp-provenance-test/SKILL.md](skills/sylp-provenance-test/SKILL.md).

Trial caveats:

- The first prompt you give uses your own plan/quota with that host. Whether to spend it is your call. Check `agent --version` / `codex --version` / `claude --version` and your plan first.
- Captured text stays local and unencrypted, which is why the repo must be a throwaway.
- Uninstall: remove the plugin folder (`~/.cursor/plugins/local/sylp-provenance`, or `~/.codex/plugins/sylp-provenance`), any `.codex/hooks.json` written by the installer, and the database under `~/.sylp-provenance`.

## What you get

`history.html` opens with **How this repository evolved**: a graph with prompts, tool windows and recorded changes on one lane and git commits on the other, edges connecting each change to the prompt and tool window behind it. Click a prompt or change node to jump to its thread below. Commits are labeled by their relationship to recorded evidence: inside a recorded tool window (possibly agent-made, not proven), during a recorded session, or outside recorded sessions. If the hooks did not fire in a live session, the page says so plainly and shows only the commits.

Below the graph, **The conversations behind the changes**: each recorded prompt as a thread - your prompt, the recorded assistant response, and the diffs produced around it, each with an evidence label (see below). Changes without a recorded prompt are grouped separately and never guessed at. Nothing is uploaded; the page makes no network calls.

## How it works: hooks, not skills

Capture uses each host's **hooks**: lifecycle events (`sessionStart`/`beforeSubmitPrompt`/`preToolUse`/`postToolUse`/`stop` on Cursor; `SessionStart`/`UserPromptSubmit`/`PreToolUse`/`PostToolUse`/`Stop`/`SessionEnd` on Codex and Claude) delivered as JSON payloads to the recorder. Hooks fire deterministically on every event, which is what makes provenance capture reliable.

Agent **skills** (SKILL.md guidance shipped in a plugin) can steer an agent's behavior, but they load at the model's discretion, carry no event payloads, and cannot guarantee that anything is recorded per edit. The plugin ships one skill and one command, but only for viewing the dashboard; capture stays on hooks. All three hosts support plugin-bundled hooks.

Each host gets a self-contained directory under `plugins/<host>/` with its manifest (`.cursor-plugin/plugin.json`, `.codex-plugin/plugin.json` plus a portable root `plugin.json`, `.claude-plugin/plugin.json`), `hooks/hooks.json`, a dashboard entry point (`commands/serve.md` or `skills/serve-dashboard/`), and copies of the shared `recorder.py` and `adapters.py`. Tests enforce that the copies never drift from the shared code.

## Host adapters

- Claude: prompt_id, session_id, tool_use_id; Claude lifecycle names retained.
- Codex: turn_id maps to the canonical prompt ID. apply_patch header paths support multiple file associations. Nonzero shell exits still use PostToolUse. No-op hook output is `{}`, including Stop. Paths declared in a patch establish association, not proof that the patch applied.
- Cursor: conversation_id/generation_id map to canonical session/turn IDs. Native camelCase events map to common recorder events. afterAgentResponse text is kept separately and linked to the corresponding turn. Missing cwd is accepted only with exactly one workspace root. Multi-root ambiguity fails visibly rather than choosing one.

Host/session namespacing prevents collisions. Missing tool IDs are rejected rather than paired by time. The generic tool pre/post path is used for Cursor, not a simultaneous afterFileEdit subscription that could double-count a change. Unknown tool names are association-only, not silently treated as file edits. Codex delayed command completion retains its pending tool window.

## Repeatable checks

```sh
python3 -m unittest discover -s tests -v
python3 demo.py /tmp/sylp-claude-fixture --host claude
python3 demo.py /tmp/sylp-codex-fixture --host codex
python3 demo.py /tmp/sylp-cursor-fixture --host cursor
```

Each demo produces its own history.html and synthetic-hooks.json. These are real file edits through simulated events, not real agent chats. Captured databases and HTML exports are not committed. The tests include native payload normalization, two-file patches, failed shell writes, delayed completion, session isolation, duplicate posts, plugin packaging integrity, the evolution timeline, and exact hook command execution from the committed plugin directories.

All host integrations remain unverified until a version-pinned live session demonstrates actual prompt IDs, file-change hooks, assistant response association, failure events and restart behavior. ## Shared recorder details

Experimental code, based on sylp main `ca79119`. No changes to the existing harness coding loop. Not released and not validated in any installed host CLI session.

## What works in the included fixture

A stdlib Python recorder stores hook boundaries and content-addressed text-file snapshots in SQLite. Each historical diff links to its prompt ID, recorded prompt and final assistant response when supplied. A self-contained HTML viewer supports filtering by filename, expanding boundary evidence, and the repository evolution timeline. It makes no network or model calls and creates no repository commits.

The demo modifies real files, sending synthetic payloads through a fresh recorder process for each event. It is not a recorded agent conversation. The core tests cover duplicate tool events, overlap, manual changes, failed-tool writes, restart state, edit/revert, exclusions, oversized files, rename handling, HTML escaping, pause and repository isolation.

## Try the deterministic fixture

Python 3.10+ and Git, no dependencies:

```sh
python3 -m unittest discover -s tests -v
python3 demo.py /tmp/sylp-provenance-example
```

Open `/tmp/sylp-provenance-example/history.html`. The output contains local fixture code and prompts. It is private unless you share it.

On repositories with many commits the graph shows the commits around the recorded activity (plus the nearest few for context) and says how many older ones are hidden. Commits carry their git author: commits by people whose sessions were never recorded on this machine appear as outside recorded sessions, because capture is per-machine and per-database - a teammate's prompts live on their machine, not in yours.

## Pause and deletion

Run the selected plugin's recorder with `pause` to stop new capture or `enable` to resume. This does not erase history. To delete history, close all recorder processes and remove the database and its `-wal` / `-shm` siblings. Delete HTML exports separately. Earlier snapshots remain after a source file is removed. No secure-erasure guarantee.

## Evidence labels

- **Tool-linked:** an Edit/Write tool named this file, and the file changed between recorded before/after boundaries. This is evidence of association, not proof that no human or other process touched it.
- **Associated:** another tool window, such as Bash, contained this change. No claimed causal attribution.
- **Ambiguous:** overlapping tool windows or an interrupted/pending operation prevent safe attribution.
- **Unattributed:** a change was observed outside a matching tool window.
- **Capture gap:** a file is no longer eligible for capture, not a verified deletion.

Rename currently appears as deletion plus addition. The viewer shows historical file diffs, not present-day line blame. Prompt-to-edit evidence is based on IDs provided by the host; missing IDs mean missing associations, not guessed ones. Commit labels in the evolution timeline describe timing relative to recorded windows, never proven authorship.

## Privacy and missing coverage

Repository opt-in authorizes local capture of submitted prompts and eligible code. Prompt text and code can contain secrets. Filename exclusions are NOT a complete secret scanner. Do not use this on sensitive repositories yet. Captured text is stored unencrypted, with restrictive file permissions. There is no remote service, telemetry or upload.

Git-ignored untracked files are excluded, plus selected credential names/directories/extensions, symlinks, binary/non-UTF8 files, files over 128KiB and snapshots over 8MiB or 2000 candidate files. Already tracked files remain candidates even if later ignored, except explicit exclusions. Capture errors are printed to stderr and do not block the host agent. There is no durable error dashboard or reconciliation after an unobserved failure yet.

Only hook-supplied submitted prompts, final assistant text and selected metadata are captured. Full transcript import, intermediate assistant messages, full tool input/output, tests-as-evidence, transcript reconciliation, automatic file watching, subagent identity display, retention/quotas, search across prompts, current-line mapping, sharing/sync and restore are NOT implemented. Edits and reversions wholly inside one tool window can be missed. Background work, concurrent sessions and manual changes can be only temporally associated. The plugin observes work; it does not execute, resume or control the host agent.
